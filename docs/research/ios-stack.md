# UnFat: iOS stack research

Date: 2026-11-03. Scope: the stack choice, a dev loop with no Mac, Live Activities, widgets, data, HealthKit, barcode scanning, CI and App Store submission. This document contains no app code.

- **Unverified** marks a claim that no primary source or test confirmed.
- **Measured** marks a timing taken from couch-remote's own GitHub Actions runs.
- Food databases, nutrition science and photo-recognition pricing are covered in `data-and-science.md`, next to this file.

## 0. Decision summary

1. **Stack: native Swift and SwiftUI**, generated by XcodeGen, built and signed on GitHub Actions macOS runners (free for a public repo). Reuses the couch-remote pipeline with one required fix: sign the archive so entitlements survive (7.3).
2. **Targets:** one app plus one widget extension holding the widgets and the workout Live Activity. **iOS 18.0**, iPhone only; iOS 26 features (Liquid Glass APIs, `HKWorkoutSession` on iPhone, Foundation Models) behind `#available`.
3. **Data:** SwiftData with the CloudKit private database, store in an App Group. iCloud sync is opt-in; HealthKit-read data never goes to iCloud (guideline 5.1.3(ii)).
4. **Rest timer without a server:** `Text(timerInterval:)` ticks on its own, a local notification marks rest end, `LiveActivityIntent` buttons wake the app. Daily calories go to widgets, not a Live Activity (8 h limit).
5. **Barcode:** VisionKit `DataScannerViewController` plus the Open Food Facts API (free, ODbL attribution).
6. **Dev loop:** CI development IPA installed from Windows over USB with go-ios (est. 5-10 min per native change), plus an in-app tuning panel for animation values. No hot reload exists for native SwiftUI on Windows.
7. **Fallback: Expo SDK 58** (dev client, `expo-widgets`, `@expo/ui`) if a 2-week spike shows the native loop is too slow.

## 1. Stack decision

### 1.1 Options compared

**Cost and release path**

| | Native SwiftUI + XcodeGen + GitHub Actions | Expo (React Native) + dev client | xtool (build on Windows/WSL) | Mac |
|---|---|---|---|---|
| Cost | 0 (public repo) | 0 on GitHub runners, or 15 EAS iOS builds a month | 0 | optional, paid |
| Release path | Existing couch-remote pipeline | EAS Submit, or `expo prebuild` plus the same pipeline | Not for release (licence risk, missing macros) | Xcode |
| Career value (Swift) | High | Medium | High | High |

**Features**

| | Native SwiftUI | Expo | xtool | Mac |
|---|---|---|---|---|
| Live Activities and widgets | First-class (ActivityKit, WidgetKit, App Intents) | `expo-widgets`, stable since SDK 56 | Widget extensions work; AppIntents macros do not | First-class |
| HealthKit | First-class | Community native module (unverified which one is maintained) | Framework is usable; unverified | First-class |
| iCloud sync | SwiftData or Core Data + CloudKit built in | No first-party option; needs a custom native module | SwiftData `@Model` unsupported; SQLiteData works | Built in |
| Apple look and animation | Native; Liquid Glass comes automatically with the iOS 26 SDK | `@expo/ui` wraps SwiftUI views; Reanimated 4 for RN views | Native | Native |
| Dev loop from Windows | CI build (1-10 min) plus install; no hot reload | JS reloads in seconds over the LAN; native changes need a rebuild | Local build plus USB install; incremental time unknown | Previews, InjectionIII |

`expo-widgets` layouts are written in JSX with `@expo/ui` and run in an isolated runtime with no hooks, no app state and no async work.

### 1.2 Dev loop timings

Measured on couch-remote, a tiny one-target app (`gh run list`, `gh run view 40139196449`):

| Step | Time | Source |
|---|---|---|
| Push to simulator compile check | ~1 min (the build step itself took 37 s) | measured |
| Dispatch to TestFlight upload | ~3.3 min wall time | measured |
| — compile job | 48 s | measured |
| — testflight job | ~2.4 min: archive 42 s, export plus upload 85 s, XcodeGen install 4-9 s | measured |
| TestFlight processing after upload | 5-30 min | unverified, varies |
| An UnFat-sized app (app, extension, SwiftData) per CI build | 3-8 min | estimate, unverified |

Loops that work without a Mac:

| Loop | Use it for | Turnaround |
|---|---|---|
| A. CI compile check on push | Compiler errors | 1-5 min |
| B. CI development IPA, installed over USB with go-ios | Native UI and logic on the real iPhone | CI time plus ~1 min |
| C. TestFlight | Release-like builds; the only way to test production CloudKit | CI time plus processing |
| D. In-app tuning panel (debug builds only) | Spring parameters, durations, spacing, colours | Seconds, on device |
| E. CI artifacts | Layout regressions | Same run as A |
| F. xtool UI playground (optional) | Pure SwiftUI view experiments | Local build |

- **B** skips TestFlight processing; needs a registered device and Developer Mode. **D** is a debug screen whose sliders drive the same constants the views read.
- **E** saves simulator screenshots or video (`xcrun simctl io booted recordVideo`). **F** needs a separate SwiftPM package without SwiftData or AppIntents and carries the licence risk below.

**Loop B details**
- go-ios ([repo](https://github.com/danielpaulus/go-ios)) runs on Windows: `ios install --path=UnFat.ipa`.
- On iOS 17+, developer services need `ios tunnel start`, with `wintun.dll` copied to `C:\Windows\System32`. Whether a plain install needs the tunnel is unverified.
- Apple Mobile Device Support (it comes with iTunes or the Apple Devices app, free) is probably required. Unverified.
- The IPA comes from an export with method `debugging`, which needs the iPhone's UDID registered in the developer portal (web). Exporting a development build with cloud signing and the API key is unverified. The fallback is `release-testing` (ad hoc), which needs the same device registration.
- Developer Mode: Apple's doc says it is required for running from Xcode and for installing an .ipa with Configurator. App Store and TestFlight installs do not need it. The doc says nothing about ad hoc installs.

**xtool details** ([repo](https://github.com/xtool-org/xtool); v1.24.0 from 2026-10-26; 14.5k stars; actively maintained)
- Builds SwiftPM-based apps on Linux or WSL, then signs them and installs them over USB. This needs a user-supplied `Xcode.xip`, usbipd-win for WSL USB passthrough, and usbmuxd. App extensions, including widgets, are configured in `xtool.yml`.
- Apple's macros come from [OpenAppleMacros](https://github.com/xtool-org/OpenAppleMacros). Not supported: SwiftData `@Model`/`@ModelActor` ([#149](https://github.com/xtool-org/xtool/issues/149); the maintainer points to GRDB or SQLiteData) and AppIntents macros; `#Preview` expands to nothing.
- Supported: SwiftUI `@Entry` and FoundationModels macros. `@Observable` needs a matching SDK and compiler ([#197](https://github.com/xtool-org/xtool/issues/197)).
- Licence risk: the Xcode and Apple SDKs agreement limits use to Apple-branded computers ([OSNews coverage](https://www.osnews.com/story/142331/xtool-cross-platform-xcode-replacement-for-linux-windows-and-macos/)). Use xtool only as a personal playground, never for release builds.

Hot reload: InjectionIII and Xcode Previews need macOS. No Windows equivalent was found.

### 1.3 Recommendation: native SwiftUI

Why:
- **Every hard feature is an Apple framework with a first-class Swift API:** ActivityKit, WidgetKit, App Intents, HealthKit, CloudKit and VisionKit. On Expo, iCloud sync and HealthKit would still need Swift or a community module, and widgets are limited by `expo-widgets`' isolated runtime.
- **The pipeline already exists.** It uploads to TestFlight in 3.3 min (measured) and needs one signing fix.
- **The Apple look comes for free.** Building with the iOS 26 SDK gives standard SwiftUI controls Liquid Glass on iOS 26 devices.
- **Expo's real advantage is only reload speed for UI work.** Loops B and D reduce that gap; they do not close it. The gap is the main risk (section 1.4).

Settings to start with:
- **Deployment target: iOS 18.0.**
  - SwiftData is more mature there than on iOS 17.
  - iOS 18 runs only on A12 and later iPhones (from Apple's device list, unverified), so the barcode scanner's hardware check always passes.
  - Alternative: iOS 26.0, if dropping iOS 18-25 users is acceptable. It removes the `#available` branches. Adoption numbers were not checked (unverified).
- **Swift 6 language mode.** Since Xcode 26, new projects default to `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and approachable concurrency, which reduces concurrency friction (unverified for CLI builds).
- **iPhone only** (`TARGETED_DEVICE_FAMILY: 1`), so no iPad screenshot set is needed.
- **Pin `runs-on` and the Xcode version.** `macos-latest` has been `macos-26` since June 2026, with Xcode 26.6 as the default; Xcode 27 images exist. Uploads must use Xcode 26+ and the iOS 26 SDK since 2026-04-28.

### 1.4 Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Slow iteration on animations and polish | More calendar time | Tuning panel (D); batch UI changes; loop B instead of TestFlight |
| Entitlements dropped by an unsigned CI archive | HealthKit, App Group and iCloud silently broken in the shipped app | Signed archive plus a `codesign` check step (section 7.3) |
| Guideline 5.1.3(ii): "may not store personal health information in iCloud" | Rejection | Sync is opt-in; no HealthKit data in CloudKit; a sync-off build can ship (section 5.3) |
| SwiftData + CloudKit constraints and bugs | Painful data model changes | Follow the constraints from day 1 (section 4.2); SQLiteData is the escape hatch |
| The app cannot update a Live Activity while suspended | Stale state on the Lock Screen | Self-updating timer views, `staleDate`, a local notification and intents (section 2.2) |
| Capabilities are not auto-registered by command-line signing (unverified) | Export fails | Pre-register App IDs and capabilities in the portal (section 7.1) |
| No local debugger or Organizer | Crashes are harder to diagnose | `os.Logger` plus an in-app log viewer; MetricKit `MXCrashDiagnostic` saved locally; TestFlight feedback |

### 1.5 Fallback: Expo

Switch criteria. Run a 2-week spike first: a skeleton app, the widget, the rest-timer Live Activity and a HealthKit read, all running on the iPhone through CI. Switch if either of these holds:
- the loop B median stays above ~15 min, or
- extension signing cannot be made to work from CI.

The Expo plan:
- **Dev client:** SDK 58 with `expo-dev-client`. Put the dev client on TestFlight with `eas build -p ios --profile development --submit` (official expo/skills `expo-dev-client` skill).
- **Connecting from Windows:** run `npx expo start --dev-client`. It serves over the LAN by default. The Windows firewall can block that; then use `--tunnel`, which needs `@expo/ngrok` ([Expo CLI](https://docs.expo.dev/more/expo-cli/)).
- **Widgets and Live Activities:** `expo-widgets` ([docs](https://docs.expo.dev/versions/latest/sdk/widgets/)).
  - Config plugin options: `groupIdentifier` (default `group.<bundleId>`), `enablePushNotifications`, `frequentUpdates`.
  - APIs: `updateSnapshot`/`updateTimeline`, and `createLiveActivity` with `start`, `update`, `end` and `getInstances`.
  - Covers the Dynamic Island compact, minimal and expanded regions, plus Lock Screen `banner`.
  - `@expo/ui` `Text` supports `timerInterval` and `countsDown`, which is enough for the rest timer.
- **Barcode:** `expo-camera` `barcodeScannerSettings` (ean13, ean8, upc_a). `launchScanner()` uses DataScanner on iOS 16+ ([docs](https://docs.expo.dev/versions/latest/sdk/camera/)).
- **Animation:** Reanimated 4, which runs on the UI thread and needs the New Architecture.
- **Gaps:** iCloud sync needs a custom native module (for example on CKSyncEngine). HealthKit relies on a community module (unverified).
- **Builds:**
  - EAS Free gives 15 iOS builds a month in a low-priority queue. EAS Starter is $19/month (optional, paid).
  - Or run `npx expo prebuild` and build on the same GitHub runner (free).
  - Since SDK 54, precompiled React Native XCFrameworks cut the RNTester clean build from ~120 s to ~10 s on an M4 Max; real apps gain less ([SDK 54 changelog](https://expo.dev/changelog/sdk-54)).
- **Ad hoc distribution:** needs `eas device:create`, and Apple can take 24-72 h to process a new device ([Expo docs](https://docs.expo.dev/build/internal-distribution/)). The TestFlight route avoids this.

## 2. Live Activities (active workout and rest timer)

### 2.1 Platform rules (Apple docs)

**Setup and limits**
- Set `NSSupportsLiveActivities = YES` in the **app** target's Info.plist.
- Lifetime: up to 8 h active, then the system removes it from the Dynamic Island. It can stay on the Lock Screen for up to 4 more hours, so 12 h at most.
- Static and dynamic data together are limited to 4 KB.
- A Live Activity has no network or location access.
- `staleDate` lets the UI show that the content is outdated.

**Starting and updating**
- Starting one generally requires the app in the foreground. A `LiveActivityIntent` can start one from the background.
- Updating or ending from the background needs background runtime.
- Push updates need a server. UnFat has none, and the design below does not need one.

**Interactivity**
- Buttons and toggles (iOS 17+) work in the Lock Screen and expanded presentations.
- Apple's docs say they are inactive on a locked device until the person authenticates. Check this on the real device.
- A `LiveActivityIntent` runs in the **app process**. A plain `AppIntent` runs in the extension process unless `openAppWhenRun` is set.

**When the app is suspended**
- A DTS engineer on the Apple Developer Forums says a suspended app cannot run timers or update its Live Activity. The only exceptions are navigation and audio apps (threads 717701 and 756278).
- One forum poster building a serverless rest timer reported a local notification arriving about a minute late. Unverified; measure it on device.

### 2.2 Rest-timer design (no server)

| Event | Runs in | Action |
|---|---|---|
| Start workout | App, in the foreground | `Activity.request(attributes:content:)` |
| Set done, inside the app | App | Update the state with `restStartedAt` and `restEndsAt`, set `staleDate`, schedule a local notification at `restEndsAt` |
| Set done, +30 s or skip, from the Lock Screen or the Island | `LiveActivityIntent`, in the app process | Same update; reschedule the notification |
| Rest ends while the app is suspended | System only | Timer text and progress reach zero on their own; the notification plays |
| Workout ends | App or intent | `activity.end(_:dismissalPolicy:)`; write the `HKWorkout` (section 5) |

The code below is a shape sketch, not final code. Labels and layout are left open.

```swift
// Shared/WorkoutActivityAttributes.swift (compiled into both targets)
struct WorkoutActivityAttributes: ActivityAttributes {
    struct ContentState: Codable, Hashable {
        var exerciseName: String
        var setIndex: Int
        var setCount: Int
        var restStartedAt: Date?
        var restEndsAt: Date?          // nil while working a set
    }
    var workoutName: String
    var startedAt: Date
}

// UnFatWidgets/WorkoutLiveActivity.swift
struct WorkoutLiveActivity: Widget {
    var body: some WidgetConfiguration {
        ActivityConfiguration(for: WorkoutActivityAttributes.self) { context in
            LockScreenView(state: context.state)              // Lock Screen banner
        } dynamicIsland: { context in
            DynamicIsland {
                DynamicIslandExpandedRegion(.leading) { /* exercise, set x/y */ }
                DynamicIslandExpandedRegion(.trailing) { RestTimer(state: context.state) }
                DynamicIslandExpandedRegion(.bottom) {
                    Button(intent: CompleteSetIntent()) { /* label */ }
                }
            } compactLeading: { /* icon */ }
              compactTrailing: { RestTimer(state: context.state) }
              minimal: { RestTimer(state: context.state) }
        }
    }
}

// Both views update without any app update or push:
Text(timerInterval: start...end, countsDown: true)
ProgressView(timerInterval: start...end, countsDown: true)
```

- **Shared code:** put the attributes and the intents in `Shared/`, compiled into both targets. The intent must exist in the app so it runs in the app process, and the extension needs the type for `Button(intent:)`. This is common practice; the exact requirement is unverified.
- **Rest-end alert:** use `UNTimeIntervalNotificationTrigger`, which needs notification permission.
- **iOS 26:** `HKWorkoutSession` now runs on iPhone ([WWDC25 session 322](https://developer.apple.com/videos/play/wwdc2025/322/)). The session covers Live Activities, Lock Screen Siri and crash recovery (`shouldHandleActiveWorkoutRecovery`). Whether an active session keeps the iPhone app running in the background, which would allow live updates, is **unverified**. The design above does not depend on it; spike it later if wanted.
- **Testing without a Mac:** the Live Activity views are plain SwiftUI. Render them in the app's debug gallery to iterate on them in loop D, then check the real presentation through loop B.

### 2.3 Daily calorie progress

- A Live Activity is a poor fit. It has an 8 h cap and must be restarted from the foreground. Apple's HIG frames Live Activities as tasks with a clear start and end (exact wording unverified).
- Use a Home Screen widget plus a Lock Screen accessory widget instead (for example an `accessoryCircular` `Gauge`). The app reloads them after each log, which costs no refresh budget (section 3).

## 3. Widgets

**Setup**
- The extension is `type: app-extension` with `NSExtensionPointIdentifier = com.apple.widgetkit-extension`.
- One `@main` `WidgetBundle` holds the calorie widgets and the `WorkoutLiveActivity`.
- Available families: `systemSmall` and `systemMedium` for the Home Screen and StandBy; `accessoryCircular`, `accessoryRectangular` and `accessoryInline` for the Lock Screen. Which ones ship is a product decision.

**Refresh budget** ([Keeping a widget up to date](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date))

| Mechanism | Counts against the budget? |
|---|---|
| The app, while in the foreground, calls `WidgetCenter.shared.reloadTimelines(ofKind:)` | No |
| A widget button runs an App Intent (the timeline reloads after `perform()`) | No |
| Timeline policy `.atEnd` or `.after(date)` | Yes: 40-70 refreshes a day for frequently viewed widgets, roughly every 15-60 min |
| `Text(timerInterval:)`, `Text(date, style: .timer)`, `ProgressView(timerInterval:)` | No reload needed ([dynamic dates](https://developer.apple.com/documentation/widgetkit/displaying-dynamic-dates)) |

**Update pattern**
- After each food log or HealthKit read, the app writes the day's summary to the App Group, then calls `reloadTimelines(ofKind:)`.
- The timeline holds one entry for now, with policy `.after(nextMidnight)` so the day resets. Keep entries at least ~5 min apart.

**Data access, simplest first**
1. **Recommended:** the app writes a tiny summary (today's totals and the goal) as JSON in the App Group container, or in `UserDefaults(suiteName:)`. The widget never opens the database. Shared `UserDefaults` needs privacy-manifest reason `1C8F.1`.
2. The widget opens the same SwiftData store through `ModelConfiguration(groupContainer:)`, read-only. A third-party pattern gives the widget `cloudKitDatabase: .none` while the app owns sync. Unverified as safe.

**Interactive widgets** ([docs](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities))
- They need iOS 17: `Button(intent:)` and `Toggle(isOn:intent:)`, with `invalidatableContent` for pending state.
- A plain `AppIntent` runs in the extension process, so a write would come from a second process into the synced store. Start read-only and spike writes later. Whether CloudKit exports changes made by the extension is unverified.

**Limits and testing**
- The widget extension memory limit is ~30 MB (commonly cited, unverified). Avoid large images and heavy work in the `TimelineProvider`.
- Without Previews or a simulator, render the widget views in the debug gallery (loop D) and check placement on the device (loop B).

## 4. Data

### 4.1 Options

| Option | iCloud sync | Sharing with the widget | Notes |
|---|---|---|---|
| **SwiftData + CloudKit (recommended)** | Built-in, private database | App Group container | Constraints in 4.2; xtool cannot build `@Model` |
| Core Data + `NSPersistentCloudKitContainer` | Built-in | App Group | Most mature; more boilerplate; same CloudKit constraints |
| [SQLiteData](https://github.com/pointfreeco/sqlite-data) (Point-Free, on GRDB; v1.12.1, 2026-10-09) | CloudKit sync and sharing ([docs](https://swiftpackageindex.com/pointfreeco/sqlite-data/main/documentation/sqlitedata/cloudkit)) | App Group | SQL with explicit migrations; works with xtool; third-party dependency |
| Local only | None | App Group | Simplest; losing the device loses the data |

Pick SQLiteData over SwiftData if SwiftData bugs block progress, if xtool builds become important, or if SQL aggregations are wanted.

### 4.2 SwiftData + CloudKit rules ([Apple](https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices), [Core Data model for CloudKit](https://developer.apple.com/documentation/coredata/creating-a-core-data-model-for-cloudkit))

**Setup**
- Capabilities: iCloud with CloudKit (container `iCloud.<bundle id>`), Background Modes with remote notifications, and the `aps-environment` entitlement. Creating containers needs an Admin or Account Holder role.
- Container setup:
  - `ModelConfiguration(schema:, groupContainer: .identifier("group..."), cloudKitDatabase: .private("iCloud..."))`.
  - Use `.none` to turn sync off.

**Model constraints**
- No `@Attribute(.unique)`.
- Every relationship is optional; no `.deny` delete rule.
- Every relationship needs an inverse (Core Data doc).
- Properties need a default value or must be optional. This is the standard rule; the pages fetched did not state it.

**Schema and environments**
- After the schema is deployed to production, changes must be additive only: new fields and new types. Never rename or delete a field.
- In DEBUG builds, initialize the schema with `NSPersistentCloudKitContainer.initializeCloudKitSchema()`. Then deploy it in the CloudKit Console, which is a web app and works on Windows.
- **Gotcha:** development-signed builds (loop B) use the CloudKit **Development** environment; TestFlight and App Store builds use **Production**. Deploy the schema to Production before testing sync in TestFlight. Widely reported; exact Apple wording unverified.

**Store layout and behaviour**
- Two configurations in one container:
  - **Synced:** food entries, meals, workouts, programs and goals.
  - **Local only** (`cloudKitDatabase: .none`): the Open Food Facts product cache and anything read from HealthKit.
  - Each configuration declares its own model types (verify in the spike).
- Daily sums: SwiftData has no aggregate fetch, so fetch and reduce in memory. That is fine at personal scale, a few thousand rows a year.
- Sync opt-in: choose `cloudKitDatabase` when the container is created, from a stored preference. Changing it means recreating the container (unverified details).

## 5. HealthKit

### 5.1 Setup ([Setting up HealthKit](https://developer.apple.com/documentation/healthkit/setting-up-healthkit), [Protecting user privacy](https://developer.apple.com/documentation/healthkit/protecting-user-privacy))

**Entitlements and Info.plist**
- Entitlement `com.apple.developer.healthkit`. Xcode also adds `com.apple.developer.healthkit.access` as an empty array.
- Do not add `health-records` (Clinical Records). Enabling it without using it risks rejection.
- `NSHealthShareUsageDescription` (read) and `NSHealthUpdateUsageDescription` (write) are both required; a missing key crashes the app at authorization.
- The Xcode GUI adds `healthkit` to `UIRequiredDeviceCapabilities`. XcodeGen does not; leave it out unless HealthKit is mandatory.

**Runtime behaviour**
- Call `HKHealthStore.isHealthDataAvailable()` first.
- A denied read is invisible: the query simply returns no data. Treat that as "no data", never as "denied".

**Review**
- A privacy policy is required (HealthKit privacy doc; guideline 5.1.1(i)). GitHub Pages hosts it for free.
- Guideline 2.5.1 asks that HealthKit use be clear in the UI and the marketing text (from memory; check the current guideline text).

### 5.2 Types and APIs

| Need | Type | API |
|---|---|---|
| Weight (read) | `HKQuantityType(.bodyMass)` | `HKSampleQueryDescriptor` for the latest sample; `HKAnchoredObjectQueryDescriptor` for changes |
| Steps (read) | `HKQuantityType(.stepCount)` | `HKStatisticsCollectionQueryDescriptor`, daily sum |
| Active energy (read) | `HKQuantityType(.activeEnergyBurned)` | Same as steps |
| Workouts (write) | `HKObjectType.workoutType()` | iOS 18-25: `HKWorkoutBuilder`; iOS 26+: `HKWorkoutSession` with `HKLiveWorkoutBuilder` on iPhone ([docs](https://developer.apple.com/documentation/healthkit/running-workout-sessions)) |
| Authorization | — | `requestAuthorization(toShare:read:)` (async), or the SwiftUI `.healthDataAccessRequest(...)` modifier (iOS 17+) |

- **Background updates** use `HKObserverQuery` with `enableBackgroundDelivery`, which needs the `com.apple.developer.healthkit.background-delivery` entitlement (from memory, unverified). This is optional: reading in the foreground and having the widget show the last summary is enough for v1.
- **Locked device:** HealthKit data is unreadable while the device is locked, so background reads can fail (from memory).
- **Writing workouts:**
  - Use activity type `.traditionalStrengthTraining` or `.functionalStrengthTraining`, with start and end dates.
  - Guideline 5.1.3(ii) forbids writing "false or inaccurate data". Writing estimated calories with a strength workout is therefore a review risk; writing only the type and duration is the safe default. This needs a product decision.

### 5.3 HealthKit and iCloud

- Guideline 5.1.3(ii) says apps "may not store personal health information in iCloud" ([guidelines](https://developer.apple.com/app-store/review/guidelines/)). 5.1.3(i) also forbids ad and data-mining uses of health data.
- Whether user-entered food logs count as personal health information is unresolved. Forum [thread 653141](https://developer.apple.com/forums/thread/653141) asks exactly this and has no answer.
- Real apps do sync diet logs through CloudKit while keeping HealthKit data on the device. Leaf's privacy policy says so. Whether such apps passed review because of that split is unverified.
- Rules for UnFat:
  1. Never write HealthKit-read samples (weight, steps, energy) to the synced store. Read them live, and cache them only in the local-only store.
  2. iCloud sync of user-entered logs is opt-in and is explained in the review notes.
  3. The app works fully with sync off. If review objects, ship that build.

## 6. Barcode and food photos

### 6.1 Scanner ([VisionKit](https://developer.apple.com/documentation/visionkit/scanning-data-with-the-camera))

| | VisionKit `DataScannerViewController` (recommended) | AVFoundation `AVCaptureMetadataOutput` |
|---|---|---|
| Minimum iOS | 16 | Any |
| Hardware | A12 Bionic or later (`isSupported`) | Any |
| Work | A `UIViewControllerRepresentable` wrapper | Manual session, preview layer and highlighting |
| Built in | Highlighting, `recognizesMultipleItems`, guidance | Nothing |

- With an iOS 18 target, every supported iPhone has an A12 or later chip (unverified), so the AVFoundation fallback is not needed. Still check `isAvailable`, which covers camera permission and restrictions.
- Use `.barcode(symbologies: [.ean13, .ean8, .upce])`. Vision is said to report UPC-A as EAN-13 with a leading 0 (unverified). Normalize codes to 13 digits and try both forms on lookup.
- `NSCameraUsageDescription` is required.

### 6.2 Open Food Facts integration ([API](https://openfoodfacts.github.io/openfoodfacts-server/api/), [licence](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/tutorials/license-be-on-the-legal-side/))

**Requests**
- Endpoint: `GET https://world.openfoodfacts.org/api/v2/product/{code}?fields=code,product_name,brands,nutriments,serving_size`.
- Reads need no auth. Use the staging environment for tests.
- Rate limits per IP: 15 requests/min for product reads, 10/min for search, and no search-as-you-type. Cache every hit in the local-only store.
- A custom `User-Agent: UnFat/<version> (<contact>)` header is required. Use a project contact, such as the repo URL or a project email, never a university address.

**Licence**
- ODbL covers the database, DbCL the contents, and CC BY-SA the images.
- Show attribution such as "(c) Open Food Facts contributors", with a link and the ODbL name.
- Share-alike applies only if an adapted database is published. An on-device cache is fine; that is a judgement, unverified.

**App Store**
- In App Store Connect, answer "uses third-party content" with yes; ODbL grants the rights.
- Coverage of Turkish products and secondary databases are covered in `data-and-science.md`.

### 6.3 Food photo recognition (platform view only; options and pricing are in `data-and-science.md`)

## 7. CI pipeline sketch

### 7.1 One-time portal setup (web, works from Windows)

1. **App IDs** (Certificates, Identifiers & Profiles), both explicit, with placeholder IDs that follow the couch-remote ASC pattern:
   - `io.github.yusufuzun03.unfat`: App Groups, HealthKit, iCloud (CloudKit), Push Notifications.
   - `io.github.yusufuzun03.unfat.widgets`: App Groups.
2. **App Group and iCloud container:** create `group.io.github.yusufuzun03.unfat` and `iCloud.io.github.yusufuzun03.unfat`, then assign them to the App IDs.
3. **Device:** register the iPhone's UDID, for loop B.
4. **App Store Connect:** create the app record with the **same** bundle ID. couch-remote had a failed run over a mismatch.
5. **Secrets:** reuse couch-remote's repository secrets: `APPLE_TEAM_ID`, `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8`.
   - Cloud-managed distribution signing needs an Admin key, or the "Access to Cloud Managed Distribution Certificate" permission.
   - The couch-remote memory note says to revoke the Admin key later. If it is revoked, UnFat needs a new key.

Whether `-allowProvisioningUpdates` creates App IDs or enables capabilities on its own is **unverified**, so pre-register everything.

### 7.3 Workflow: what changes from couch-remote

**Critical gotcha.** couch-remote archives with `CODE_SIGNING_ALLOWED=NO`.
- Entitlements live inside the code signature (DTS, [thread 720887](https://developer.apple.com/forums/thread/720887)), so an unsigned archive carries none.
- CouchRemote has no entitlements, so it was unaffected. UnFat would ship without HealthKit, App Group and iCloud entitlements.

**Fix.** Sign ad hoc at archive time, then let the export re-sign with the cloud-managed certificate.
- These flags are reported in [thread 756119](https://developer.apple.com/forums/thread/756119) and are said to match how Xcode Cloud invokes the build.
- Verify them in the first spike run with the check step below.

Everything not shown stays as in couch-remote's `ios.yml` (secret check, key write and removal, the `export.plist` heredoc). Changes:

```yaml
on:
  workflow_dispatch:
    inputs:
      target: { type: choice, options: [compile, device-ipa, testflight], default: compile }
jobs:
  build:
    runs-on: macos-26                    # pinned, not macos-latest
    steps:
      - run: sudo xcode-select -s /Applications/Xcode_26.6.app   # pin; check runner-images for installed versions
      # compile mode: unchanged simulator build with CODE_SIGNING_ALLOWED=NO (no entitlements needed there)
      - name: Archive (ad hoc signed so entitlements are kept)
        run: |
          set -eo pipefail
          xcodebuild archive -project UnFat.xcodeproj -scheme UnFat \
            -destination 'generic/platform=iOS' -archivePath "$RUNNER_TEMP/UnFat.xcarchive" \
            CODE_SIGN_STYLE=Automatic DEVELOPMENT_TEAM="$APPLE_TEAM_ID" \
            CODE_SIGN_IDENTITY=- AD_HOC_CODE_SIGNING_ALLOWED=YES \
            CURRENT_PROJECT_VERSION="${{ github.run_number }}" | tail -n 40
      - name: Fail if entitlements are missing
        run: |
          app="$RUNNER_TEMP/UnFat.xcarchive/Products/Applications/UnFat.app"
          codesign -d --entitlements :- "$app" | grep -q com.apple.developer.healthkit
          codesign -d --entitlements :- "$app/PlugIns/UnFatWidgets.appex" | grep -q application-groups
      - name: Export
        run: |
          # export.plist "method"/"destination": testflight -> app-store-connect/upload,
          # device-ipa -> debugging/export (fallback: release-testing). Same -allowProvisioningUpdates
          # and -authenticationKey* flags as couch-remote.
      - uses: actions/upload-artifact@v4
        if: inputs.target == 'device-ipa'
        with: { name: UnFat-ipa, path: "${{ runner.temp }}/export/*.ipa", retention-days: 3 }
```

### 7.4 CI gotchas

**Signing and versions**
- **The bundle ID must match the ASC record**, or the upload fails. couch-remote hit this.
- **Build numbers:** `github.run_number` restarts if the workflow file is renamed or recreated, and ASC rejects a duplicate build number. Keep the file name stable, or add an offset.
- **Extension versions:** the extension's `CFBundleShortVersionString` and `CFBundleVersion` must equal the app's. Passing `CURRENT_PROJECT_VERSION` on the command line applies it to all targets.
- **`aps-environment`:** CloudKit needs it. Whether the CLI export rewrites `development` to `production` is unverified. Check the exported IPA with `codesign -d --entitlements :-`, after unzipping `Payload/UnFat.app`.
- **Development export:** cloud-managed development signing with the API key (method `debugging`) is unverified. If it fails, use `release-testing` (ad hoc). Both need the registered device.

**Public repo**
- Never commit `*.p8`, `*.mobileprovision` or `*.p12`; add them to `.gitignore`.
- Do not use `pull_request_target` in iOS workflows. Fork PRs get no secrets, which is fine.
- Artifacts of public repos are downloadable by signed-in GitHub users (unverified). Keep retention short. A development IPA installs only on registered devices.

**Runners and cost**
- Standard GitHub-hosted runners are free for public repos. A private repo would get $12/month of included usage, with macOS at $0.062/min ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
- Optional speed-up: cache SwiftPM checkouts (`-clonedSourcePackagesDirPath` plus `actions/cache`). Skip it until package resolution shows up in the timings.

## 8. App Store submission checklist

**Account and records (web)**
- [ ] App IDs, App Group, iCloud container and capabilities registered (section 7.1).
- [ ] ASC app record created: check that the name "UnFat" is available, set the primary language and the SKU.
- [ ] The free-apps agreement is enough. The Paid Apps agreement is needed only for a price or in-app purchases.

**Build requirements**
- [ ] Built with Xcode 26+ and the iOS 26 SDK; this has been required since 2026-04-28 ([Apple upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)). Expect the next SDK bump around spring 2027 (unverified).
- [ ] Entitlement check passes on the exported IPA (section 7.4).
- [ ] CloudKit schema deployed to Production before TestFlight (section 4.2).
- [ ] App icon: a single 1024x1024 PNG in the asset catalog; dark and tinted variants can be added as extra PNGs. Icon Composer's layered `.icon` format needs a Mac, so skip it.
- [ ] `ITSAppUsesNonExemptEncryption = false`, which answers export compliance for HTTPS-only apps.

**Privacy**
- [ ] Privacy policy URL, required for every app and especially HealthKit apps. GitHub Pages hosts it for free.
- [ ] Support URL (for example the repo's issues page or a Pages page).
- [ ] `PrivacyInfo.xcprivacy` in the app and the extension, listing required-reason APIs ([Apple](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)): `UserDefaults` `CA92.1` (own app) and `1C8F.1` (App Group); add file-timestamp, boot-time or disk-space codes only if used. Codes are from memory (unverified); check Apple's list.
- [ ] App Privacy questionnaire ([definitions](https://developer.apple.com/app-store/app-privacy-details/)): "collect" means sent off the device and kept longer than needed to serve the request. With no analytics or crash SDKs the likely answer is "Data Not Collected". Open: whether the CloudKit private database counts (likely not, unverified) and how to label Open Food Facts lookups (section 9).

**Store listing**
- [ ] Screenshots ([specs](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications)): one 6.9" portrait set (1320x2868, 1290x2796 or 1260x2736), 1-10 images, no alpha; smaller sizes scale from it, no iPad set for an iPhone-only app. Use real iPhone captures if the resolution matches, else a CI Pro Max simulator (`xcrun simctl io booted screenshot` or XCUITest); upload via the ASC web UI.
- [ ] Age rating questionnaire. Apple updated the age-rating system in 2025, and health and wellness topics have their own question (unverified details).
- [ ] Third-party content declared (Open Food Facts, ODbL), with attribution visible in the app.
- [ ] A disclaimer that calorie and macro numbers are estimates, not medical advice (guideline 1.4.1 territory; wording is a product decision).

**Review**
- [ ] Review notes: no login needed; how to see the Live Activity (start a workout); why HealthKit is used; the iCloud sync opt-in and that no HealthKit data goes to iCloud.
- [ ] HealthKit use visible in the UI and the description (2.5.1). No Clinical Records entitlement.
- [ ] Let users delete their data inside the app, including the CloudKit records. Good practice; account-deletion rules do not apply without accounts.
- [ ] TestFlight internal testing first (no review needed), then submit.

## 9. Open questions and unverified points

- **Guideline 5.1.3(ii) and iCloud.** Do user-entered food logs count as "personal health information"? No answer from Apple was found. The design keeps sync opt-in and keeps HealthKit data local.
- **CLI signing.** Does `-allowProvisioningUpdates` with an API key register capabilities, and does it support development (`debugging`) exports through cloud signing? Pre-register; fall back to `release-testing`.
- **Ad hoc archive flags.** Does archiving with `CODE_SIGN_IDENTITY=-` followed by export produce correctly entitled IPAs for both targets? The CI check step will answer this on the first run.
- **iOS 26 `HKWorkoutSession` on iPhone.** Does an active session grant background runtime to update the Live Activity? This is not needed for the baseline design.
- **go-ios on Windows.** Does a plain install on iOS 17+ need the wintun tunnel, and is Apple Mobile Device Support required?
- **App Privacy labels.** How should Open Food Facts lookups be labelled? A barcode is sent to a third party with no user identifier. Decide when filling in the questionnaire.
- **xtool licence.** The Xcode and SDK agreement limits use to Apple hardware. Personal-risk decision; never use xtool in the release path.
- **Deployment target.** iOS 18.0 (recommended) or iOS 26.0. This is a product call that depends on target users and on which iOS the developer's own iPhone runs.
